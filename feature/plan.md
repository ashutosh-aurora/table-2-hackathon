# Session plan

**Date:** 2026-06-17  
**Table:** Mixed dev + product managers  
**End users:** External clients (Aurora's clients) and internal colleagues

## Table position

Close to use cases — the table spans product and engineering, with a clear external client in view. That means the problem hunt should focus on **client-facing seams**: where Aurora's clients hit friction understanding model outputs or methodology.

## Stated direction

Two candidate problems have already surfaced:
1. **AI chat interface for methodology Q&A** — clients can ask questions about how Aurora's models work and how methodology choices connect to specific results.
2. **Real-time decision visualisation** — helping clients (or internal users) see how decisions are being made as they unfold.

Both point at the same underlying risk: clients trust (or don't trust) Aurora's outputs without being able to interrogate the reasoning behind them.

## Who brings what

- **Product managers:** own the "what does the client actually want?" — keep them on user need and value framing throughout.
- **Developers:** own feasibility checks and prototype build — bring them in hard when the slice is chosen.

## Time allocation (hackathon block: 13:30–16:30)

| Time | What |
|---|---|
| ~30 min | Problem loop — land on one problem, name it |
| ~20 min | Frame it — outcome, scope, success criteria |
| ~20 min | Solution loop — shape to a slice |
| ~90 min | Prototype — build the cheapest thing that tests the risk |
| ~20 min | Retro and naming |

## Notes

- The two candidate problems are related but distinct — the problem loop should sharpen which one is *more felt* and *more sliceable today*.
- The chat interface problem is likely closer to a prototype today; the decision visualisation problem may need more shaping first.
- Thin context on the client side (no specific user research quoted) — treat that as a gap to name during framing, not a blocker.
